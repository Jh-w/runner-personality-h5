### 2.1 为什么不做技术栈变更

v4.3 是**维度扩展**而非架构翻新，以下评估均指向「不做变更」：

| 候选变更 | 评估结论 | 理由 |
|----------|----------|------|
| React 19 → 其他框架 | ❌ 不换 | 16→32型扩展是纯数据引擎变更，不涉及框架能力边界。迁移成本 >> 收益 |
| Vite 8 → 其他构建工具 | ❌ 不换 | 构建产物 ~310KB gzip，构建时间 ~360ms，无性能瓶颈 |
| TypeScript 类型系统 | ✅ 充分利用 | v4.3 新增 `FlavorDimension`、`FlavorScores`、扩展 `Dimension`、`PersonalityTypeId`(1-32) 等类型，TypeScript 的类型安全在 32 型扩展中发挥了关键作用——编译期捕获了所有编码映射遗漏 |
| GitHub Pages → 其他托管 | ❌ 不换 | 纯静态 SPA，GitHub Pages 免费 + CDN + 自定义域名，无迁移动力 |
| 引入后端 API | ❌ 不需要 | 风味判定和 5 维计分均为纯前端计算，无服务端依赖需求 |
| 引入状态管理库 (Redux/Zustand) | ❌ 不需要 | useTestEngine hook + progressStore 已足够。18 题状态机复杂度可控 |

## 3. 5维计分引擎：核心算法变更

### 3.1 从 4 维到 5 维的算法扩展

v3.0 的计分引擎是项目的技术核心。v4.3 对其进行了项目史上最深层的变更。

**v3.0（4维/16型）逻辑**：

```
四维度每题 ±1 计分
  → signKey(scores) 生成 4 字母编码（如 "CSGP"）
  → lookup 16 型映射表（key: 4字母编码, value: typeId 1-16）
  → 结果页渲染 4 维度解读
```

**v4.3（5维/32型）逻辑**：

```
18题 → 15道计分题（每维3题）+ 3道风味题
  → calculateScores(15个计分答案) → DimensionScores { motivation, social, style, ritual, expression }
  → signKey(scores) 生成 5 字母编码（如 "CSGP_D"，下划线分隔）
  → lookup 32 型映射表（key: 5字母编码, value: typeId 1-32）
  → 结果页渲染 5 维度解读
```

### 3.2 关键设计决策：下划线分隔

5 字母编码中，位置 2（social: S/G）和位置 3（style: D/P）和位置 5（expression: D/A）存在字母重用风险。

| 编码位置 | 维度 | 可能值 | 潜在歧义 |
|----------|------|--------|----------|
| 位置2 | social | S（独狼）/ G（社群） | — |
| 位置3 | style | D（计划）/ P（随性） | D 与位置5的 D 冲突 |
| 位置5 | expression | D（数据派）/ A（氛围派） | D 与位置3的 D 冲突 |

**决策**：使用下划线分隔前 4 维和第 5 维（`CSGP_D`），而非拼接成无分隔的 5 字母串（`CSGPD`）。理由：

1. **可读性**：`CSGP_D` 一眼可知前 4 维是 CSGP，第 5 维是 D
2. **避免歧义**：`CSGPD` 的最后一个 D 无法区分是 style=D 还是 expression=D
3. **向后兼容**：前 4 位仍然与 v4.1 的 4 字母编码完全一致，方便跨版本对比

### 3.3 SignKey → TypeId 映射表设计

```typescript
// 32 型完整映射（2^5 = 32）
const TYPE_MAP: Record<string, PersonalityTypeId> = {
  'CSDG_D': 1,  'CSDG_A': 2,   // 竞技·独狼·计划·装备
  'CSDM_D': 3,  'CSDM_A': 4,   // 竞技·独狼·计划·极简
  'CSPG_D': 5,  'CSPG_A': 6,   // 竞技·独狼·随性·装备
  'CSPM_D': 7,  'CSPM_A': 8,   // 竞技·独狼·随性·极简
  'CGDG_D': 9,  'CGDG_A': 10,  // 竞技·社群·计划·装备
  // ... 共 32 条
  'EPM_D': 31,  'EPM_A': 32,   // 体验·独狼·随性·极简
};
```

**设计要点**：
- 映射表是常量，编译时完全确定，无运行时动态生成
- TypeScript `Record<string, PersonalityTypeId>` 保证类型安全
- 任一 5 字母编码有且仅有一个 typeId 映射——编译期穷举 + 运行时 fallback（unknown → typeId 1）

## 4. 风味维度：独立计分体系

### 4.1 为什么风味标签独立于人格维度

v4.3 新增的「风味标签」与 5 个人格维度有本质区别：

| 对比维度 | 人格维度（motivation/social/...） | 风味标签（time/injury/diet） |
|----------|----------------------------------|------------------------------|
| **判定方式** | 3道题累加 → signKey 判定（二元） | 1题1标签 → 直接映射（4选1） |
| **参与 signKey** | ✅ 是 | ❌ 否 |
| **影响人格类型** | ✅ 决定 typeId | ❌ 不参与 |
| **影响分享卡片** | ✅ 5维标签条 | ✅ 风味角标 |
| **存储位置** | `DimensionScores` | `FlavorScores`（独立字段） |

**核心决策**：风味标签**不与 signKey 耦合**。这是项目最重要的架构决策之一。

**如果风味参与 signKey**：时间(4值) × 伤痛(4值) × 饮食(4值) × 32型 = **2048 种组合**，完全不可维护。

**独立判定的优势**：
1. 人格类型保持 32 型的可管理规模
2. 风味标签可以独立迭代（增删改标签不影响人格计分）
3. 分享卡片上「人格名 + 风味角标」的组合已有丰富的个性化（32 × 4 × 4 × 4 = 2048 种展示组合，但只是乘法而非枚举）

### 4.2 风味判定算法

```typescript
// 风味题不进入 dimensionScore 累加
function calculateFlavorScores(answers: Answer[]): FlavorScores {
  return {
    time:   getAnswerForQuestion(answers, 16).flavorValue,  // 'morning'|'night'|'flexible'|'anytime'
    injury: getAnswerForQuestion(answers, 17).flavorValue,  // 'panic'|'careful'|'ignore'|'listen'
    diet:   getAnswerForQuestion(answers, 18).flavorValue,  // 'fuel'|'reward'|'balance'|'whatever'
  };
}
```

风味题的 `Question` 结构使用独立的 `flavorDimension` 字段，不污染计分题的 `dimension` 字段：

```typescript
export interface FlavorQuestion {
  id: number;
  text: string;
  flavorDimension: 'time' | 'injury' | 'diet';  // 独立字段
  options: {
    id: string;
    text: string;
    emoji: string;
    flavorValue: string;  // 直接映射值
  }[];
}
```

## 5. 动物插图渲染方案

### 5.1 背景

v4.2.5 已完成动物插图的资产准备：32 个动物 PNG（~5.3KB 每个）存放在 `public/animals/animal-type-{01-32}.png`。v4.3 直接复用，无新增资产。

### 5.2 渲染链路

```
ResultPage
  └── TypeIllustration
        ├── 优先：<img src="/animals/animal-type-{XX}.png" alt={animalName} />
        └── fallback：<span>{animalEmoji}</span>（emoji 圆形容器）
```

`CanvasRenderer`（分享卡片生成）从画 SVG 跑者小人改为画动物 PNG：

| v4.1 | v4.3 |
|------|------|
| `ctx.drawImage(svgRunner, ...)` | `ctx.drawImage(animalPng, ...)` |
| SVG 内联渲染，依赖浏览器 SVG 解析 | PNG 直接 blit，性能更好 |
| 分享卡片上有 SVG 跑者图标 | 分享卡片上有动物 PNG + 5维标签 + 风味角标 |

### 5.3 技术选型：PNG 而非 SVG/WebP

| 方案 | 评估 | 结论 |
|------|------|------|
| SVG | Canvas `drawImage` 对 SVG 支持不一致（Safari 有已知 bug） | ❌ |
| WebP | 文件更小但 Safari 兼容性问题 | ❌ |
| PNG | 所有浏览器完美支持 Canvas drawImage；5KB × 32 ≈ 170KB 总资产，可接受 | ✅ |

## 6. 数据方案：从4维到5维+风味的埋点升级

### 6.1 埋点方案保持不变

v3.0 确定的「纯前端埋点」方案在 v4.3 中**不作变更**：
- 仍使用前端事件埋点（神策/GrowingIO SDK）
- 仍无后端 API
- 仍无实时排行榜

### 6.2 v4.3 埋点变更

v4.3 需要在 v3.0 埋点基础上，对关键事件新增维度字段：

| 事件 | v4.1 属性 | v4.3 新增属性 |
|------|----------|--------------|
| `test_complete` | `personality_type`（4字母）, `dimension_scores`（4维） | `personality_code`（5字母 `X_X`）, `dimension_scores.expression`, `flavor_scores`（time/injury/diet） |
| `answer_select` | `dimension`（motivation/social/style/ritual） | `dimension` 新增值 `expression`；风味题发送 `flavor_dimension` 而非 `dimension` |
| `result_view` | `personality_type` | 新增 `flavor_time`, `flavor_injury`, `flavor_diet` |
| `share_card_generate` | `personality_type` | 新增 `flavor_time`, `flavor_injury`, `flavor_diet` |

**personality_code 5字母编码格式**：

| 位置 | 维度 | 含义 |
|------|------|------|
| 1 | motivation | C（竞技）/ E（体验） |
| 2 | social | S（独狼）/ G（社群） |
| 3 | style | D（计划）/ P（随性） |
| 4 | ritual | G（装备）/ M（极简） |
| `_` | 分隔符 | 固定 |
| 5 | expression | D（数据派）/ A（氛围派） |

示例：`CSGP_D` = 竞技·独狼·社群·计划·数据派

### 6.3 风味标签埋点

风味标签在 `test_complete` 事件中作为独立字段上报：

```json
{
  "event": "test_complete",
  "properties": {
    "personality_code": "CSGP_D",
    "personality_type_id": 5,
    "dimension_scores": {
      "motivation": -2,
      "social": -1,
      "style": 1,
      "ritual": -1,
      "expression": -2
    },
    "flavor_scores": {
      "time": "morning",
      "injury": "panic",
      "diet": "fuel"
    }
  }
}
```

### 6.4 新增统计口径

| 指标 | 计算口径 | 用途 |
|------|----------|------|
| **32型人格分布** | `test_complete` 按 `personality_type_id` 分组 COUNT | 相比 16 型，分布更分散，更容易出现「稀有类型」社交货币 |
| **5维得分分布** | `dimension_scores.expression` 的分布 | 验证表达维度区分度 |
| **风味标签分布** | `flavor_scores.time/injury/diet` 交叉统计 | 内容运营素材（如「晨型跑者中 60% 是数据派」） |
| **风味×人格交叉** | `personality_type_id` × `flavor_scores` 交叉分析 | 发现「数据稳态者大多早晨跑步」等洞察 |

## 7. 进度持久化：版本迁移策略

### 7.1 问题

v4.3 的答题数从 12 题变为 18 题，计分维度从 4 维变为 5 维。`sessionStorage` 中存储的旧版进度（v4.1/v4.2.5 的 12 题答案）与 v4.3 的计分引擎不兼容——直接用旧进度计分会得到错误的人格类型。

### 7.2 决策：硬版本号 + 旧进度丢弃

```typescript
// progressStore.ts
const CURRENT_VERSION = 4;  // v4.1 = 3, v4.3 = 4

function loadProgress(): SessionData | null {
  const raw = sessionStorage.getItem(STORAGE_KEY);
  if (!raw) return null;
  const data = JSON.parse(raw);
  if (data.version !== CURRENT_VERSION) {
    // 版本不匹配 → 丢弃旧进度，从头开始
    sessionStorage.removeItem(STORAGE_KEY);
    return null;
  }
  return data;
}
```

**为什么不尝试迁移旧进度？**

| 方案 | 评估 | 
|------|------|
| 自动迁移（12→18题） | 需要补 6 道题的默认答案，但用户可能已经流失（隔几天回来），补的答案没有用户意图，计分无意义 |
| 保留 12 题 + 跳过新 6 题 | 计分引擎是 5 维的，12 题答案缺少 expression 维度数据，无法映射到 32 型 |
| 丢弃旧进度 | 用户损失 ≤ 2 分钟（12 道已答），但获得准确的 32 型结果。简单可靠 |

**决策**：丢弃策略。版本号不匹配 → 清除旧进度 → 用户从 Q1 重新开始。用户体验上表现为「上次没测完，这次重来吧」，损失可控。

## 8. 结论与行动项

### 8.1 核心决策总结

| 决策项 | v4.1/v4.2.5 | v4.3 决策 | 理由 |
|--------|-------------|-----------|------|
| **技术栈** | React 19 + Vite 8 + TS 6 | ✅ 不变 | 维度扩展不触及框架能力边界 |
| **计分维度** | 4 维（signKey 4字母） | 🔴 5 维（signKey 5字母 + `_` 分隔） | 产品需求驱动，表达方式是独立人格维度 |
| **人格类型** | 16 型（2⁴） | 🔴 32 型（2⁵） | 5 维二元的自然结果 |
| **风味标签** | 无 | 🆕 独立于 signKey 的 3 维判定 | 避免 2048 种组合爆炸 |
| **题目数** | 12 题 | 🔴 18 题（12+3+3） | 15 道计分（每维 3 题）+ 3 道风味 |
| **动物插图** | PNG（v4.2.5 已就绪） | ✅ 完全复用 | 资产已存在，渲染链路从 SVG→PNG |
| **埋点方案** | 纯前端埋点 | ✅ 不变，仅新增字段 | 风味标签和 expression 维度作为新字段上报 |
| **部署方式** | GitHub Pages | ✅ 不变 | 纯静态 SPA |
| **后端 API** | 无 | ✅ 仍不需要 | 风味判定纯前端计算 |
| **进度迁移** | version=3 | 🔴 version=4，旧进度丢弃 | 5 维计分无法兼容 4 维旧答案 |
| **构建产物** | ~310KB gzip | ~312KB gzip（+2KB） | 新增 flavorScoring.ts + 32型数据 + 6道题 |

### 8.2 v4.3 技术风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|:---:|------|----------|
| 32 型中某些类型罕见到无人被测出 | 中 | 低（不影响功能，只是该类型结果页无人看到） | 保持 16 型作为 fallback 展示（B 计划），PRD 中有降级方案 |
| 5 字母编码的前后端/分析工具兼容性 | 低 | 中 | 埋点平台需支持 `_` 字符的字段值；已验证神策/GrowingIO 支持 |

### B. 技术名词解释

| 术语 | 解释 |
|------|------|
| **signKey** | 将 DimensionScores 转换为编码字符串的函数，如 {motivation:-2, social:1, style:-1, ritual:1, expression:-2} → "CSPM_D" |
| **风味维度** | 独立于人格计分的 3 维标签（晨型/夜跑/灵活/随时 × 恐慌/谨慎/无视/倾听 × 燃料/犒劳/平衡/随便），不参与 signKey 判定 |
| **typeId** | 人格类型唯一标识符，1-32 的整数。UI 层通过 typeId 获取数据，不直接使用编码 |
| **5 字母编码** | 格式 `XXXX_X`，其中 `_` 为固定分隔符。前 4 位对应 motivation/social/style/ritual，第 5 位对应 expression |
| **B 计划** | 16 型 fallback。如果 32 型中某类型数据不完整或占比极低，降级展示 16 型版本 |
